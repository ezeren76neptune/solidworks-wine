# What breaks under Wine, and what fixes it

Every fix that was needed is listed here, grouped by when it bites. "Wine" means Wine 11.20 (Fedora build) unless noted. Several of these are plain gaps in Wine and would be better fixed upstream. If you take one there, please link it here.

## Installing

| Symptom | Cause | Fix |
|---|---|---|
| The installer stub exits at once, asking for "Internet Explorer 10 or later" | The stub checks `GetProcAddress(wininet, "HttpWebSocketReceive")`, and Wine's wininet has no such export | `install/patch-ie10-check.py` flips the one conditional jump after that probe in the staged copies of `setup.exe`, `StartTUI.exe` and `setup_noUAC.exe` |
| The installer aborts on the OS check | It requires Windows 11 | `winetricks win11` (in `setup-prefix.sh`) |
| The installer reports the wrong .NET version | It checks for the .NET 4.8.1 release number | The `Release` value is set to 533320. .NET 4.8 from winetricks runs everything it needs |
| `--multi` answer file is ignored | The file must be a JSON *list* of `{mode, data:{volumes, vars, env}}` | `install/make-install-json.py` |
| .NET install or `ngen` hangs, or the wineserver asserts in `get_server_inproc_sync` | Wine 11's in-process ntsync path under .NET load | `sw-wine` hides `/dev/ntsync` (bubblewrap bind of an unreadable file), so wineserver falls back to server-side synchronisation |
| The VC11 prerequisite step fails | Wine's builtin `msvcr110` and friends have no version resource | `native,builtin` DLL overrides. The installer puts Microsoft's real DLLs in place |
| SOLIDWORKS MSI fails in `InstallSpatialIOP` | The step unzips with the Windows shell's zip-folder API, which Wine lacks | Condition set to `0` in the MSI. `spatialiop.zip` is unpacked with 7z into `SOLIDWORKS\spiop\files` and `Visualize\Plugins\sp.x` |
| SOLIDWORKS MSI rolls back in `SWRegistration` | Some regsvr32 registrations fail under Wine: the property handler, the Design Checker OCX, DFMXpress, and `swdocumentmgr.dll` failing to load | The custom action type gets +64 ("continue on error"): 3073 → 3137 |
| SOLIDWORKS MSI "succeeds" but installs almost nothing | Wine's MSI does not add the parents of the features named in `ADDLOCAL` | `install/install-msis.sh` passes the full feature list a Windows install ends up with (`install/solidworks-addlocal.txt`), via a `.bat` because argv quoting mangles `PROP="a b"` |
| Help, manuals and examples get installed even though Windows skips them | Wine honours `msidbFeatureAttributesFollowParent` differently | `install/feature-fix.sql` clears that flag (attributes 10 → 8) on the 25 features Windows leaves absent |
| Dictionary compile (`JS0CORBADicExe`) fails late in the install | It needs `ntdll!RtlIsNameInExpression`, which no Wine or Proton release has up to 11.20 | Added to the private ntdll copy (`tools/rtl_isnameinexpression.c`), with the DOS wildcard semantics `*`, `?`, `<`, `>` and `"` |

## Starting and signing in

| Symptom | Cause | Fix |
|---|---|---|
| "Missing WebView2 runtime", or a plain Wine username/password box instead of the 3DEXPERIENCE page | No WebView2 runtime in the prefix. The loader looks for `EdgeUpdate\Clients\{F3017226-…}` and `EdgeUpdate\ClientState\{F3017226-…}\EBWebView` | `install/install-webview2.sh`. **Don't type your password into Wine's box.** |
| The WebView2 window is blank, or its GPU process fails | It needs DirectComposition swap chains, and its sandbox fails under Wine. Dassault's `WebView2Loader.dll` (2021) ignores the `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` variable | `sw-wine` sets `--no-sandbox --disable-gpu --disable-gpu-compositing` as the policy `HKLM\Software\Policies\Microsoft\Edge\WebView2\AdditionalBrowserArguments`, value name `*` (the runtime ignored it under HKCU or under the exe name), and `AppDefaults\msedgewebview2.exe\Version=win7` |
| The sign-in page shows, then turns white a few seconds later except where the mouse just was. No text cursor in the fields | msedgewebview2.exe draws the page into a child of the launcher's window. A process cannot use another process's window surface, so Wine draws such a child straight onto the X11 window, and the launcher's next surface flush puts its own white copy back over it | `tools/patch-wineserver.py`: wineserver keeps a parent's surface off child windows owned by another process, as it already does for OpenGL/Vulkan children (`PAINT_HAS_PIXEL_FORMAT`). Bound over the system wineserver by `sw-wine` |
| Jagged, unevenly spaced text on the sign-in page | The 1998-2000 core fonts from `winetricks corefonts` have `gasp` tables that ask for grid-fitting without grayscale at about 9-17 pixels. Chromium then draws them like bitmap fonts | `tools/fix-font-gasp.py` adds grayscale to those ranges, as in the fonts current Windows ships. `sw-wine` runs it once per prefix |
| Once the saved sign-in has expired, every start shows Wine's grey "Authentication Required" username/password box. OK brings it back or leaves SOLIDWORKS stuck, and Cancel brings it back | The launcher checks `/api/user/authn/status`. The server answers 401, either with no `WWW-Authenticate` header or with only `CAS realm='CAS Server'`, because the sign-in is a web page. Dassault's HTTP client then calls `InternetErrorDlg(ERROR_INTERNET_INCORRECT_PASSWORD)`. Windows draws that dialog from the authentication scheme, so for these responses it shows nothing and the launcher opens its WebView2 sign-in page. Wine shows its password box for any 401. With no scheme to answer, whatever is typed there is never sent | `tools/wininet_errordlg.c` replaces the `InternetErrorDlg` export of the private wininet copy (`pe-inject.py --replace`). When a 401/407 offers no Basic, Digest, NTLM, Negotiate or Kerberos challenge, it returns `ERROR_CANCELLED` without a dialog. Every other case goes to Wine's own dialog |
| Crash right after sign-in (a jump through a null pointer in `JS0LCC`) | `wininet!InternetSetCookieEx2` is missing, and the launcher uses it to hand the sign-in cookies to WinINet | Added to a private wininet copy (`tools/wininet_setcookieex2.c`), built on Wine's `InternetSetCookieExW` |
| `cannot load JS0PCC.dll`, then a crash in `JS0GROUP` | Dassault's in-memory DLL loader, used for one of its own modules, needs the non-exported Windows loader functions `LdrpHandleTlsData` and `LdrpReleaseTlsEntry`. It finds them by scanning ntdll's code, and Wine's ntdll has neither | `tools/ntdll_add.c` implements both on Wine's own TLS tables (mirroring `alloc_tls_slot` in Wine's `loader.c`). `pe-inject.py --ldrp-tls` lays out the string, the `lea` and the Windows 10 prologue the scanner looks for, each jumping to those implementations. The module itself is not modified, and licensing works exactly as on Windows: you sign in with your account |
| Stuck at "Loading registry…" for minutes | Wine's computer name is the Linux hostname cut to 15 characters. SOLIDWORKS resolves it, and the lookup waits for DNS timeouts | `sw-wine` gives the process tree a hosts file that maps that name to 127.0.0.1 |
| Crash in `comctl32` while "Loading task panes…" | A task pane sends `HDM_LAYOUT` with a NULL `HDLAYOUT`. Windows returns FALSE, while Wine dereferences it | `tools/patch-comctl32.py` adds the NULL check to a copy of `comctl32_v6.dll`. The prefix's winsxs copy is the one Wine maps, so the wrapper binds over both |
| Crash in `concrt140` (`GetProcessorCount` stub) | Wine's concrt140 lacks it | `native,builtin` override for the VC14 runtime. The installer puts Microsoft's DLLs in place |

## Using SOLIDWORKS

| Symptom | Cause | Fix |
|---|---|---|
| The 3D view stays black | With "Enhanced graphics performance" on, SOLIDWORKS makes OpenGL calls with no current context | Turn it off: Tools > Options > Performance |
| Hang with an `X_CopyArea BadMatch` error (seen on NVIDIA), or a black view | EGL backend of Wine's X11 driver | `X11 Driver\UseEGL=N` (GLX) |
| The PropertyManager's green check and other buttons do nothing | Wine sends `WM_CAPTURECHANGED` to a window that keeps the capture. The buttons' subclass then drops the click between button-down and button-up (Wine bugs 27403, 58668, 59478) | `tools/patch-win32u.py` applies Denis Bonnenfant's patch from bug 27403 in binary form: in `set_capture_window`, skip the message when the previous window is the same one |
| On an NVIDIA GPU (PRIME render offload), the 3D view stops updating: new geometry, view changes and sketches don't appear, or only stale frames and edges show | SOLIDWORKS presents its viewports by drawing into the front buffer and calling `glFlush`; it never calls SwapBuffers. With PRIME offload, the NVIDIA driver only copies a frame to the window, which the integrated GPU displays, on a buffer swap. SOLIDWORKS also uses the back buffer as scratch: it clears it, draws overlays such as the view triad there and copies the changed strips to the front buffer, so front and back must stay separate (mapping front onto back, as Wine's EGL backend does, made the part vanish when hovering the triad or under a dialog). Wine's `EmulateModeset` framebuffer surfaces keep them separate, but on NVIDIA they fail with `GLXMakeContextCurrent` BadMatch, because Wine's internal contexts use pixel format 1 while SOLIDWORKS uses a depth/stencil format | In `SW_GPU=nvidia` mode, `tools/patch-win32u-nvidia.py` routes every GL window through framebuffer surfaces (an FBO with separate front and back, presented with a real swap), creates the window's real drawable with pixel format 1 to match Wine's internal context, and binds application contexts to a null surface of their own format, so only the internal context touches the window |
| On an NVIDIA GPU, sketch dimensions and other drag previews leave trails: every position the preview passed through stays on screen | SOLIDWORKS saves the finished view with the `GL_KTX_buffer_region` extension and restores it to erase each preview frame. Only NVIDIA's driver offers that extension (Mesa doesn't, so the integrated GPU is not affected). The save and restore miss the FBO SOLIDWORKS actually draws into, so nothing gets erased | In `SW_GPU=nvidia` mode the wrapper sets `HKCU\Software\Wine\AppDefaults\sldworks.exe\OpenGL\DisabledExtensions` to `GL_KTX_buffer_region`, which Wine honours by hiding the extension and its functions. SOLIDWORKS then redraws the view instead, as it does on Mesa |
| On an NVIDIA GPU, SOLIDWORKS disappears in the middle of saving (`X_GLXMakeContextCurrent` BadMatch in the output) and leaves a 0-byte file | Saving renders the preview image stored in the file into a bitmap (a memory DC) with a bitmap pixel format: single-buffered, RGB, 24-bit depth. Wine backs the bitmap with a pbuffer of that format and copies between the two in `flush_memory_dc()` with its internal context, which has pixel format 1 (double-buffered RGBA, no depth). Mesa accepts the pairing; NVIDIA's GLX refuses it, and Xlib's default error handler ends the process | In `SW_GPU=nvidia` mode, `tools/patch-win32u-memdc.py` copies the rendered image back with SOLIDWORKS' own context, which has the pbuffer's format, when it is the active context reading from that pbuffer (otherwise the copy is skipped), and skips uploading the bitmap's old contents into a new pbuffer |
| Opening a part hangs on NVIDIA: the main thread is stuck resizing the task pane, and the embedded browser's GPU process is gone | Direct3D (DXVK) runs on the NVIDIA GPU in the same session. The exact cause was not found | `SW_GPU=nvidia` keeps DXVK on the integrated GPU with `DXVK_FILTER_DEVICE_NAME`, detected from `/sys/class/drm` (Intel or AMD), and drops the `NV_optimus` Vulkan layer |
| Typing in a PropertyManager number box keeps only the first character: `12` becomes `1.00in`, and text typed after the value gets added to it (`2.00in3` = 5 in) | Each keystroke makes SOLIDWORKS show a small popup: a tooltip, or a "Filter Quick Hits" suggestion list over the box. Wine maps these as managed X windows and the window manager offers them the focus. Wine accepted those offers, including late ones after SOLIDWORKS had already re-activated its main window (set_net_active_window() skipped telling the window manager about the main window because Wine still recorded it as the requested one). The box lost the focus, SOLIDWORKS committed and reformatted the value, and the next keys went to the graphics area | `tools/patch-winex11-focus.py`: WM_TAKE_FOCUS for a caption-less popup that is not the foreground window is refused, and set_net_active_window() always sends the activation request when the active window actually changes, so Wine ignores the window manager's stale activation of the popup |
| In PropertyManagers (Extrude, Dimension, ...) the group headers ("From", "Direction 1", ...) and some check boxes show for a moment and then disappear; the header rows stay empty except for the collapse arrows | SOLIDWORKS paints each group by reading its header button's current rectangle, adding a 4 px margin and calling `SetWindowPos(header, HWND_TOPMOST, ...)`, on every `WM_PAINT` and every `WM_PRINTCLIENT` (which themed check boxes send to draw their background). On Windows that moves nothing: a child window given `HWND_TOPMOST` or `HWND_NOTOPMOST` keeps its position and size (Wine's own user32 test, `todo_wine`). Wine moved the header, which uncovered part of the page, which painted again: the headers slid right 4 px per paint until they were 0 px wide | `tools/patch-win32u.py`: in `set_window_pos()`, a child window moved with `HWND_TOPMOST`/`HWND_NOTOPMOST` gets `SWP_NOMOVE \| SWP_NOSIZE`, as on Windows; z-order handling is unchanged. Test: `tools/tests/pmdrift.c` |
| In PropertyManagers some check boxes are blank: the Extrude PropertyManager's "Draft outward" and the check box in front of "Direction 2" (the label next to it still shows) | Themed check boxes paint their background with `DrawThemeParentBackground`, which sends the parent `WM_ERASEBKGND` and `WM_PRINTCLIENT` with the check box's own paint DC. SOLIDWORKS' PropertyManager page ends its `WM_PRINTCLIENT` handler with `ReleaseDC(page, hdc)` on that DC. Windows releases a DC whatever window is named (Wine's user32 tests), and Wine also disables a released cache DC, so everything the check box drew afterwards (box and label) was lost. On Windows the button paints through a buffered-paint memory DC, so the parent never gets the window DC | `tools/uxtheme_parentbg.c`, injected into a private `uxtheme.dll` by `tools/pe-inject.py`, replaces `DrawThemeParentBackground`: it copies what is under the control into a memory DC, runs Wine's function on that, and copies the result back. Test: `tools/tests/pmdrift.c` |
| A toolbar tooltip stays on screen after opening its flyout (View Orientation in the heads-up toolbar) and pressing Escape, until another button is hovered | Wine's TrackMouseEvent keeps tracking hover and leave while another window holds the mouse capture, so the graphics area got WM_MOUSEHOVER under the open flyout and showed a balloon that no WM_MOUSELEAVE ever hid. Windows tracks the window that receives mouse input, which is the capture window, and sends the tracked window WM_MOUSELEAVE. Wine's leave check also skipped hit-testing (window_from_point without WM_NCHITTEST) | `tools/patch-win32u.py`: get_mouse_window() hit-tests and treats a capture held by another window as the window under the cursor |
| The S-key shortcut bar has a black block or strip beside its buttons | SOLIDWORKS paints the bar off-screen: the toolbar gets `WM_PRINTCLIENT` (or `WM_PAINT` with a DC) for a memory bitmap that starts out black. Wine's toolbar erases its background only in `BeginPaint` or, in v6, with `TBSTYLE_TRANSPARENT`, so on that path nothing was erased; SOLIDWORKS draws behind each button itself, and the area without a button (the bar is as wide as its search box) stayed black. With a theme, the erase also hands `WM_ERASEBKGND` to the parent, which may claim it without painting | `tools/patch-comctl32.py`: the supplied-DC call to `TOOLBAR_Refresh` first runs the toolbar's own erase (fix 3, found through the DLL's COFF symbols), and that erase fills with `COLOR_BTNFACE` before asking the parent (fix 2) |
| The Open/Save dialogs are Wine's, not the desktop's | Wine implements the Vista-style IFileDialog itself and has no way to show the desktop's file dialog | `tools/swfiledlg.c` (built into `swfiledlg.dll`) is registered for `CLSID_FileOpenDialog` and `CLSID_FileSaveDialog`. It wraps Wine's dialog object, forwards every call to it and records the title, file types, folder, file name and options; `Show()` runs `kdialog` through `/bin/sh` instead (Wine can start Linux programs with CreateProcess), keeps the owner window disabled and repainting until it returns, and answers GetResult/GetResults/GetFileName/GetFolder from the chosen path. The file type index comes from the chosen file's extension, because kdialog does not report the selected filter. Controls the application adds with IFileDialogCustomize keep their defaults |
| A folder SOLIDWORKS asks Windows to open (open/explore, or showing a file in its folder) appears in Wine's own file browser | Wine's shell sends folders to its `explorer.exe` by DDE (`folder\shell\open\ddeexec`), and ShellExecute refuses to start a Linux program itself | `tools/swopenfolder.exe` (built by `tools/build-pe.sh`) becomes the Folder class's open and explore command and starts Dolphin (`$SW_FILE_MANAGER`, else `xdg-open`) with the Linux path; `sw-wine` registers it and removes the DDE entry |
| "Show in Folder" (Welcome dialog > Recent > Documents) does nothing | It calls `SHOpenFolderAndSelectItems`, which in Wine only works with Wine's explorer: it runs the Folder "explore" verb through ShellExecuteEx with an ID list, and for an ID list Wine puts the folder into the whole command line and then looks that line up as one file name, so a command with arguments never starts | `tools/shell32_openfolder.c`, injected into a private shell32 copy (`pe-inject.py --replace`, which now keeps forwarded exports): turns the item into a path and starts `swopenfolder.exe /select,"path"` (Dolphin shows the file selected), else Wine's function |
| "Segoe UI is not available" when opening parts or templates, and missing symbols (□) in some lists | Segoe UI and Segoe UI Symbol are Windows fonts, not included | Font replacements in the prefix: Segoe UI and its weights → Noto Sans, Segoe UI Symbol → DejaVu Sans (`install/setup-prefix.sh`) |
| The Open dialog's left pane shows Wine's My Computer, Trash and "/" instead of your folders | Wine's dialog builds that pane from the desktop namespace. Windows-style "folder shortcut" namespace items (`Instance\InitPropertyBag\Target`) are ignored by Wine's shell32 | `tools/swplaces.c` is a small COM DLL that serves such items using Wine's own FolderShortcut class. `tools/sync-places.py` registers your file manager's places and hides Wine's items (`SFGAO_NONENUMERATED`) |
| Double-clicking a part in the file manager doesn't start SOLIDWORKS properly | Wine's file associations call plain `wine` | `install/fix-desktop-entries.sh` |

## How the patched files are made

`sw-wine` never touches the system's Wine. On each start it:

1. hashes the system's `ntdll.dll`, `wininet.dll`, `shell32.dll`, `uxtheme.dll`, `comctl32_v6.dll`, `win32u.so`, `winex11.so` and `wineserver`;
2. builds a patched copy of each into `tools/build/` the first time a hash is seen;
3. bind-mounts each copy over the original, for the SOLIDWORKS process tree only, through bubblewrap.

After a Wine update, new copies are made automatically. The patchers look for exact byte patterns. If a pattern is missing in a new Wine build, the patcher refuses and writes nothing. The wrapper then goes on without that fix, except for ntdll, where it stops, so check its output.

- `tools/build.sh` compiles `ntdll_add.c` and `wininet_setcookieex2.c` as freestanding, position-independent blobs: no imports, `-fPIE`, a flat linker script.
- `tools/pe-inject.py` adds such a blob to a PE DLL. It puts the blob in a new `.swx` section and rebuilds the export directory. It also fills "slots" in the blob with the distance to DLL exports (`slot_<name>`) or to internal symbols from the DLL's COFF symbol table (`symslot_<name>`). The blob can then call into the DLL without relocations.

Tests (Windows programs, built with the prefix's `csc.exe` or MinGW) are in `tools/tests/`:

- `rtltest` checks `RtlIsNameInExpression`;
- `cookietest` checks `InternetSetCookieEx2`;
- `tlstest` checks the TLS functions; pass it a DLL that has a TLS directory;
- `placestest` checks the file-dialog places.
